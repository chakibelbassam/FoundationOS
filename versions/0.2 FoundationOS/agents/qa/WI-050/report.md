### WI-048 sub-check note (scroll-cancelled hover reveal)

- Hover dwell → reveal works in the browser with real pointer input: `data-revealed` flipped to `true` after a real hover (multiple times, including a no-scroll control).
- Deliberate click and keyboard activation still work after the hover-reveal machinery (rows 11 and 19).
- **Scroll-cancel of a *pending* dwell could not be conclusively reproduced interactively**: the browse relay is too slow/lossy to land a real scroll inside the 1000 ms dwell (`DWELL_MS`), and the background tab throttles page-side `setTimeout`, so scheduled in-page scrolls fired late or not at all. Recorded as a tooling gap (F5), **not** a product failure: the regression is covered by the passing unit test `cancels a pending hover dwell when the page or a nested surface scrolls` (AppCard.test.tsx, within `npm test`), and the code path is confirmed (`AppCard.tsx`: capturing window scroll listener → `clearDwell()`; once revealed, the reveal persists until Close/navigation, and pointer exit only cancels a pending dwell).

### WI-048 / F5 on the built-in surface (retried at 6397d26) — **GAP**

Attempted on a fresh stack with real input where possible: `/folder` root shelf (full page and inside the 390×600 qa frame), gated on a **closed** card (`data-revealed="false"`), scroll headroom reserved, positive controls run. What prevented staging, in order of attempts:

1. The built-in snapshot/refs do not descend into the qa helper's iframe (no element refs inside the frame; `find` at all depths returns nothing for frame content), so the card could not be addressed for `hover` at first. A frame-scoped snapshot (`frames` + `snapshot({ frameID })`) does produce refs and one real `hover` sequence did start the dwell (reveal observed).
2. That real-pointer dwell start does not reproduce on re-hover: with the pointer verifiably over the card (element `:hover` matches), `data-revealed` never flips on hover alone — repeated on the full page and in the frame (4 attempts, 14–16 probes ≈ 2.5–3 s each, including a pointermove+pointerover variant). Click activation reveals fine; the CSS hover state updates; the JS pointer handler behind the 1 s dwell does not run for the built-in hover. Without a startable dwell, a *pending* reveal to cancel does not exist.
3. Synthetic `PointerEvent` dispatch does not drive React's dwell either (non-bubbling `pointerenter`, bubbling `pointerover`, and pointerId-1 move+over variants all left `data-revealed` false through the dwell window), so an in-page substitute could not be used; page-side `setTimeout` scheduled inside evaluate calls also does not survive the call (isolated world teardown), removing the fallback used in the first pass.

The scroll-cancel behaviour therefore remains verified only by the passing unit regression ("cancels a pending hover dwell when the page or a nested surface scrolls", within `npm test` 80/80) and the code path (capturing window scroll listener → `clearDwell()`). No product claim is made either way; this is a tooling/harness limitation of the built-in browser surface, unchanged in substance from the first pass.
